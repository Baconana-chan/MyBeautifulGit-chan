# TODO — MyBeautifulGit-chan

Git GUI, который даёт **весь** git и не притворяется нянькой. Никаких «эта кнопка недоступна,
потому что мы решили, что вам это не нужно»: удалить уже закоммиченный коммит, переписать
историю, сделать force-push, поправить конфиг руками — всё это должно быть в UI, а не только
в терминале.

Безопасность достигается не запретами, а **понятностью и откатом**: показать точную команду,
показать последствия, сделать бэкап-ссылку, дать Undo через reflog.

## 0. Манифест

- [ ] **Git — не песочница.** Если git это умеет, приложение это умеет.
- [ ] **Не прячем — предупреждаем.** Опасная операция не блокируется, а объясняется: что
      произойдёт, что станет недостижимым, как откатить.
- [ ] **Каждое действие — это git-команда.** Пользователь всегда видит, что именно выполнилось,
      и может скопировать/повторить это в терминале. Никакой «магии» и скрытых переписываний.
- [ ] **Escape hatch всегда рядом.** Встроенный терминал и запуск произвольной git-команды —
      первоклассная фича, а не закопанная настройка.
- [ ] **Откат вместо запрета.** Перед переписыванием истории — backup-ref; журнал операций +
      reflog + «Undo» на любое действие.
- [ ] **Скорость — часть UX.** Большие репозитории (linux, chromium) не должны превращать UI в
      слайд-шоу.
- [ ] **Клавиатура прежде мыши**, но мышью можно всё.

## 1. Чего приложение НЕ делает (и почему это не «ограничения»)

- Не реализует собственную семантику git поверх чужой библиотеки — источник правды всегда git.
- Не скрывает команды «для вашей безопасности». Максимум — свернуть в «Advanced».
- Не блокирует force-push, reset --hard, rebase, filter-repo, удаление веток/тегов на remote.
- Не отправляет телеметрию.

## 2. Технические решения

### 2.1 Git-бэкенд

**Решение: нативный `git` CLI как основной бэкенд (Desktop), libgit2/JGit — только там, где CLI
физически недоступен (Android).**

Почему не JGit/libgit2 как основной:

- «Все возможности git» и «библиотека, которая догоняет git» — взаимоисключающие вещи. JGit
  отстаёт по протоколам, конфигам, `filter-repo`, sparse-checkout, worktree-деталям, хукам,
  подписям, LFS.
- Поведение должно совпадать с терминалом 1:1, включая ошибки и вывод хуков.
- Пользовательские alias, `includeIf`, credential helper, SSH-агент, GPG — всё работает
  бесплатно, потому что это тот же git.

Правила работы с CLI:

- [ ] Все вызовы через один `GitProcess`-слой: `ProcessBuilder`, отключённый pager, принудительный
      `--no-color`, `core.quotepath=false`, `LC_ALL=C` для парсинга, отдельный stderr.
- [x] Чтение статуса, лога и refs через стабильные plumbing-форматы:
      `status --porcelain=v2 -z`, `log --pretty=format:...`, `for-each-ref --format=...`.
- [ ] `diff --raw -z`, `diff --numstat -z`, `ls-files -s -z` для остальных экранов.
- [x] Запись — обычные porcelain/plumbing-команды, без «умных» обёрток, меняющих смысл.
- [ ] Все команды логируются (без секретов) в журнал операций: команда, cwd, exit code,
      длительность, stderr.
- [ ] Отмена долгих операций: kill дерева процессов + предупреждение про `index.lock`.
- [ ] Прогресс (`clone`, `fetch`, `push`, `gc`) — парсинг stderr с `--progress`.
- [ ] Креды: `GIT_TERMINAL_PROMPT=0` + собственный `GIT_ASKPASS`/`SSH_ASKPASS`; собственные
      токены и пароли — в encrypted store (не в конфиге и не в OS-keychain). Настроенный
      пользователем credential helper git может использоваться как внешний механизм.
- [x] `git` не найден / старая версия: экран с вариантами установки, ручной путь, проверка
      минимальной версии и список недоступных фич.
- [x] **Решение: только системный git.** Ищем `git` в PATH и стандартных путях; если не найден —
      предлагаем автоматическую установку по кнопке (Windows: Git for Windows; macOS:
      `xcode-select --install` или Homebrew; Linux: пакетный менеджер дистрибутива) с системным
      подтверждением прав; плюс ручной выбор пути. Встроенный git в 1.0 не бандлим.

### 2.2 Android

**Решение: Android не входит в 1.0.** Сначала стабильный desktop-релиз; Android — отдельный
этап после него. Это не «запрет», а порядок работ: Android-бэкенд не должен размывать
готовность ПК-версии.

Android не содержит git и не даёт нормального random-access к произвольной папке через SAF —
это ограничение платформы.

- [x] Зафиксировать стратегию: Android после 1.0; основной путь — libgit2/JGit in-process,
      Termux — только опциональный power-user bridge, не основной бэкенд.
- [ ] После 1.0 выбрать libgit2 или JGit по результатам прототипа.
- [ ] Termux bridge (если делаем): отдельное приложение/UID, репозиторий только в доступной
      обоим памяти, SAF не подходит, Play-сборка Termux без RUN_COMMAND — только F-Droid/GitHub.
- [ ] Честно маркировать в UI, какие операции недоступны на Android и почему (со ссылкой на
      ограничение платформы, а не «мы спрятали»).

### 2.3 Архитектура кода (KMP, Compose Multiplatform)

Текущий каркас: `shared/src` (common), `shared/src@jvm`, `shared/src@android`,
модули описаны в `*/module.yaml`, сборка — `./kotlin build`.

Предлагаемая структура:

```
shared/src/
  domain/        # RepoState, Commit, Ref, WorkingTreeEntry, Operation, ...
  git/           # GitBackend (interface), GitCommand, GitResult, GitError, парсеры
  ops/           # сценарии: stageHunk, rebaseInteractive, reset, push, undo
  ui/            # экраны и компоненты Compose
  ui/state/      # ViewModel-и, состояние экранов (StateFlow)
shared/src@jvm/
  git/cli/       # CliGitBackend, ProcessBuilder, askpass, progress
  platform/      # файловые диалоги, secrets (encrypted store), открытие терминала
shared/src@android/
  git/           # libgit2/JGit-бэкенд (позже)
  platform/      # SAF, хранение
```

- [x] `GitBackend` — интерфейс без «удобных» упрощений: принимает произвольную команду и
      возвращает структурированный результат (это гарантирует отсутствие потолка возможностей).
- [ ] Очередь операций **на репозиторий**: две записи одновременно не идут, читающие — можно.
- [x] Обработка `index.lock`: детект, объяснение, «удалить lock» — явной кнопкой.
- [x] File-watcher на `.git` + рабочее дерево, debounce и ручной refresh.
- [ ] Кэш и инвалидация производных данных (история, diff, refs).
- [x] Ошибки git показываются как есть (stderr), плюс человеческое пояснение и «copy command».
      `ErrorBanner` распознаёт формат `command → exit N`, показывает локализованное объяснение,
      раскрывает оригинальный stderr (после redaction секретов) и копирует точную команду.

### 2.4 Производительность

- [x] Граф коммитов строим сами (parent-ы из `log --topo-order`), а не парсим
      ASCII-граф — нужен для виртуализации и фильтров.
- [x] Инкрементальная загрузка истории (страницы по 200), ленивый diff, LRU-кэш по OID.
- [ ] Виртуализованные списки везде, где может быть 100k+ строк.
- [ ] Никаких блокирующих вызовов в UI-потоке; все операции — cancellable.
- [ ] Бенчмарк-набор: репозиторий на ~1M коммитов, 200k файлов в worktree, бинарные файлы.

### 2.5 Encrypted store (секреты)

Мастер-ключ шифрует store; сам мастер-ключ оборачивается device key из OS keystore и, опционально,
вторым слоем passphrase. Оба слоя разворачивают один и тот же мастер-ключ, поэтому смена passphrase
не перешифровывает данные.

- [ ] Формат: `magic | version | kdf_id | kdf_params | salt | nonce | ciphertext | tag`.
      `kdf_id`: 1 = Argon2id, 2 = PBKDF2-SHA256 (fallback). `version` обязателен — иначе миграция
      невозможна.
- [ ] Шифрование только AEAD: AES-256-GCM или XChaCha20-Poly1305. CBC без MAC не используем.
      AAD = `magic || version || kdf_params`, чтобы параметры KDF нельзя было подменить.
- [ ] Миграция v1 → v2: читаем старый `kdf_id`, расшифровываем старым ключом, шифруем новым,
      пишем атомарно (temp + fsync + rename). Старый файл не удаляем до успешной верификации
      нового.
- [ ] Смена KDF (например, усилили Argon2id) — переwrap мастер-ключа, а не перешифровка всего
      store.
- [ ] Восстановление: device-bound без passphrase — восстановления нет, UI говорит это прямо,
      а не «упс». С passphrase — recovery-код (мнемоника 12/24 слова или base32), хранится
      у пользователя. «Секретный вопрос» не делаем.

### 2.6 Совместимость с версиями git

Минимум — **2.30** (декабрь 2020): базовый сценарий работает целиком. Полный запланированный
набор появляется к **2.40**; 2.56 для 1.0 не нужен.

| Возможность | Появилась в |
|---|---|
| `push --force-if-includes` | 2.30 |
| `diff --merge-base` | 2.30 |
| `worktree repair` | 2.30 |
| `rev-parse --path-format` (внутреннее) | 2.31 |
| `commit --fixup=amend:/reword:` | 2.32 |
| `commit --trailer` | 2.32 |
| `stash push --staged` | 2.35 |
| `status --porcelain=v2 --show-stash` | 2.35 |
| `log/show --remerge-diff` | 2.36 |
| `worktree list --porcelain -z` | 2.36 |
| `gc --cruft` (cruft-паки) | 2.37 |
| `rebase --update-refs` | 2.38 |
| `merge-tree --write-tree` | 2.38 |
| `merge-tree --merge-base` | 2.40 |
| `git history drop` (эксперим.) | 2.56 |

`sparse-checkout add` — 2.26, `git maintenance` — 2.29, поэтому на 2.30 они уже есть.

Что теряется на 2.30 и как компенсируем:

- `rebase --update-refs` — зависимые ветки после переписывания двигаем сами через `update-ref`
  или предупреждаем, что они остались на старых коммитах.
- `merge-tree --write-tree` / `--merge-base` — превью конфликтов пробным merge с откатом;
  на 2.38 доступно без изменения worktree, на 2.40 — с явной базой.
- `stash push --staged` — на 2.30 недоступен; вкладка `STASH` отклоняет его, а частичный
  stash по выбранным файлам и `-u`/`-a` работают.
- `commit --fixup=amend:/reword:` — обычный `--fixup` + интерактивный rebase.
- `--remerge-diff`, cruft-паки — опциональные advanced-виды/режимы gc, не блокируют 1.0.

**EOL — это мягкое предупреждение, а не жёсткий минимум.** У Git нет формального календаря
EOL: upstream держит security-ветки неопределённое время (на ноябрь 2026 — примерно 2.52+,
при этом 2.47 уже считают EOL сторонние трекеры), а дистрибутивы бэкпортируют патчи в
2.34/2.39/2.43. Если привязать hard minimum к upstream-EOL, приложение перестанет открываться
на Debian 12, Ubuntu 22.04/24.04 и RHEL 9, хотя их git получает патчи.

- **hard minimum (2.30)** — порог возможностей; ниже — экран установки/обновления.
- **EOL-баннер** — версия ниже `oldestSecuritySupported` (2.52 на момент 1.0), но выше
  hard minimum: не блокируем; пишем «ветка не получает upstream-патчи, в LTS-дистрибутиве
  проверьте пакет», показываем недоступные фичи и кнопки обновления.
- **partial** — версия ниже `fullToolset` (2.40): «часть возможностей недоступна» + список.
- Повторный баннер — не чаще раза на версию git/релиз приложения, с «не напоминать для этой
  версии».

Политика зашита в релиз (`GitSupportPolicy`), без сети и телеметрии; обновляется вместе с
приложением. Авто-обновление git — только по явной кнопке и с системным подтверждением прав;
на Linux — пакет дистрибутива, не случайный бинарник.

2.56 не требует ни одна базовая фича: `git history` ещё экспериментален,
`git refs create/delete/...` заменяется `update-ref`.

Версии сверены по upstream `Documentation/RelNotes`; `ReleaseNotes.html` в Git for Windows
описывает только Windows-специфику.

## 3. UX-концепция

### 3.1 Каркас окна

- [ ] Левая панель: **Branches / Remotes / Tags / Stash / Worktrees / Submodules** — единый
      список с поиском, а не пять вкладок.
- [ ] Центр: **граф истории** (основной экран, а не «вторая вкладка»).
- [ ] Правая/нижняя область: **diff** выбранного коммита/файла + метаданные.
- [ ] Нижняя панель: **Changes / Console** (журнал операций и терминал).
- [ ] Верхняя строка состояния: текущая ветка, ahead/behind, состояние merge/rebase, число
      stash, detached HEAD, «идут операции».
- [x] Мультирепозиторий: вкладки репозиториев, drag&drop папки в окно.

### 3.2 Опасное, но доступное

- [ ] Диалог опасной операции показывает: точную команду, что изменится, какие коммиты станут
      недостижимыми (сколько и каких), есть ли они на remote, когда истечёт reflog.
- [ ] Кнопка «сделать backup-ref» включена по умолчанию для переписывания истории.
- [ ] Никаких «мы не разрешим» — только «вот что произойдёт» и ввод имени ветки/хеша для
      подтверждения самых разрушительных сценариев.
- [ ] Force-push: `--force-with-lease` как дефолт, но `--force` и произвольный refspec — доступны
      явно, с объяснением разницы.
- [ ] Reset: `--soft / --mixed / --hard / --keep`, с превью содержимого index и worktree.

### 3.3 Откат

- [x] Журнал операций приложения: что, когда, чем закончилось, как отменить.
      Вкладка `HISTORY` объединяет журнал и undo/redo: время, точная команда, результат, доступность
      отмены; отменённые записи остаются в истории, новая операция очищает redo-ветку.
- [ ] Undo/Redo для операций поверх git (reset, rebase, commit, checkout, push).
- [ ] Панель Reflog: все переходы HEAD и веток, восстановление коммита/ветки в один клик.
- [ ] Snapshot-refs вида `refs/mybeautifulgit/backups/<timestamp>-<op>` перед переписыванием.
- [ ] «Restore from backup» — даже после `reset --hard` и `gc`.

### 3.4 Клавиатура и обнаруживаемость

- [x] Command palette (`Ctrl/Cmd+K`): **все** команды, включая разрушительные, с поиском по
      названию, git-команде и описанию. Палитра работает в главном окне и окнах worktree,
      ищет по нескольким словам, поддерживает `↑/↓`, `Enter`, `Esc` и помечает опасные действия.
- [ ] Горячие клавиши на всё основное; шпаргалка (`?`).
- [ ] Контекстные меню не единственный путь к функции — всё доступно и через палитру/меню.
- [ ] Подсказки «что дальше» в пустых состояниях (нет репозитория, нет коммитов, конфликт).
- [x] Локализация ru/en: системная локаль по умолчанию, переключатель в шапке, `ui.language`
      в `settings.properties`.
- [ ] Тёмная/светлая/системная тема, настройка шрифта (моно) и размера.

### M6 — Переписывание истории (ядро продукта)

- [x] **Интерактивный rebase** как полноценный редактор todo-листа:
      drag&drop коммитов, `pick / reword / edit / squash / fixup / drop / exec / break /
      label / reset / merge`, autosquash, edit-todo во время выполнения. План снимается пробным
      `git rebase -i --rebase-merges`; todo и `reword`-сообщения передаются через
      `GIT_SEQUENCE_EDITOR`/`GIT_EDITOR`, после завершения доступен Undo по backup-ref.
- [x] **Удаление уже закоммиченного коммита** — все честные способы, каждый объяснён:
      `drop` в rebase (сохранить потомков), `reset --hard` (отрезать хвост), `revert`
      (без переписывания), `filter-repo` (вычистить из всей истории). Диалог показывает
      точную команду, последствия и доступность способа: drop открывает todo с выбранным
      коммитом в `drop`; reset идёт на родителя и создаёт backup-ref/Undo; revert для merge
      отклоняется без mainline; filter-repo требует установленный `git filter-repo`, чистый
      worktree без stash, создаёт bundle всех refs и не отменяется обычным Undo. filter-repo
      удаляет коммит из всех refs, но, в отличие от rebase, не вычитает его diff из деревьев
      потомков — это явно указано в диалоге.
- [x] Reset soft/mixed/hard/keep с превью потерь.
- [x] Amend/reword любого коммита, изменение авторства, разбиение коммита (`edit` + reset).
      Reword поддерживает root/merge-target, если среди потомков нет merge; split/amend требуют
      обычного коммита, а диапазоны с merge-потомками отклоняются явно.
- [x] Перестановка коммитов, `rebase --onto`, перенос диапазона, squash диапазона.
      Диалог `history rewrite` даёт четыре режима: соседний swap через `rebase -i` (произвольный
      порядок остаётся в drag&drop редакторе todo), `git rebase --onto` для текущей ветки,
      перенос `A..HEAD` на новый base и squash `A..B` (A исключается; первый коммит получает
      сообщение, остальные становятся `fixup`). У всех операций есть проверки чистого worktree,
      backup-ref и Undo; merge-коммиты для swap/squash отклоняются явно.
- [x] `git filter-repo`: удаление файла/папки/секрета из истории, замена строк, переписывание
      путей; предпросмотр и обязательный backup-ref.
      Отдельный диалог `filter-repo` работает по всем локальным refs: `--invert-paths --path`
      для файла/папки, `--replace-text` через временный expressions-файл для секрета/строк и
      `--path-rename` для путей. Перед запуском обязательны `--dry-run` предпросмотр с числом
      коммитов/refs/путей и подтверждение; создаются backup-ref в `refs/mybeautifulgit/backups`
      и bundle всех refs, а backup-ref исключён из `--refs`, чтобы filter-repo его не переписал.
      Секрет не попадает в командную строку/лог; expressions-файл удаляется после операции.
- [x] Backup-refs + Undo для каждой операции переписывания: reset, `commit --amend`,
      reword, split/amend и интерактивный rebase. Tip сохраняется в
      `refs/mybeautifulgit/backups/<millis>-<n>-<operation>-<short-hash>` до мутации;
      toast предлагает Undo, а при грязном worktree изменения сначала уходят в stash.
- [x] Cherry-pick/revert диапазона, `--no-commit`, разрешение конфликтов в процессе.
      Диапазон задаётся как `A..B`; для `--no-commit` коммиты применяются по одному, а после
      разрешения конфликта и stage continue применяет следующий. Обычный range использует
      OperationBanner с continue/abort/skip; при конфликте сразу открывается merge editor.
- [x] Планировщик «что станет недостижимым» до выполнения (`rev-list` diff + `fsck`).
      Reset и rewrite-диалоги показывают коммиты, уникальные объекты и уже недостижимые
      объекты; учитываются остальные refs, reflog/backup остаются путём восстановления.

### M11 — PR-помощник (уровень 1 в 1.0; API — после 1.0)

Цель — не «магический PR», а объяснимый навигатор: показать, где репозиторий, какие права
у текущего аккаунта, что именно произойдёт, и дать точные команды. В 1.0 входит только
**уровень 1 — Custom Git Host** (разбор remote и локальный preflight без API-обещаний).
Identity, права и PR/MR-адаптеры — после 1.0; зависят от M4 (remotes) и §2.5 (encrypted store).
Подробная дорожная карта 1.1: [TODO-1-1.md](./TODO-1-1.md) — GitHub/GitLab adapters,
provider-фундамент, интеграция в UI и немецкая локализация.

Сначала M11 работает как **уровень 1 — Custom Git Host**: любой разбираемый git-remote без
провайдерских обещаний. Затем добавляются **уровень 2 — адаптеры конкретных хостеров**.
Уровень 1 не зависит от API и не блокирует обычные git-операции; уровень 2 расширяется
после 1.0: первые два адаптера — в 1.1, остальные — в 1.2–1.9. Весь набор сразу не обещаем.

#### M11.1. Remote и identity

- [x] `RemoteUrlParser`: scp-like (`git@github.com:owner/repo.git`), `ssh://`, `https://`,
      `git://`, локальные пути, порты, несколько URL у одного remote, `insteadOf`; имя `origin`
      не считать признаком владельца. Реализовано для уровня 1 в 1.0.
- [x] Определять host + owner/repo. Неизвестный или self-hosted хост → `UNKNOWN`, без догадок
      по имени папки, email автора коммита или названию remote. Уровень 1 показывает
      `CUSTOM`/`UNKNOWN` и локальный preflight; forge-права остаются `UNKNOWN`.
- [ ] Получать identity текущего аккаунта (`GET /user` для GitHub/GitLab); поддержать несколько
      аккаунтов и явный выбор активного.
- [ ] Вход на первом этапе — PAT в encrypted store, с минимальными scopes. OAuth/device flow —
      позже. Токен никогда не попадает в `settings.properties`, логи, URL или журнал операций.
- [ ] Кэш метаданных, ETag и обработка rate limit/offline. Сетевые ошибки не блокируют обычные
      git-операции и не превращаются в ложное «read-only».

#### M11.2. API и права

- [ ] GitHub: `GET /repos/{owner}/{repo}` — `fork`, `parent`, `source`, `default_branch`,
      `permissions.push`/`admin`; при возможности GraphQL `viewerPermission`.
- [ ] GitLab: `GET /projects/:id` — `forked_from_project`, `permissions.project_access`,
      `default_branch`; `GET /user` для identity.
- [ ] Публичные репозитории без токена: только публичные метаданные. Права в этом случае —
      `UNKNOWN`, а не «read-only по умолчанию».
- [ ] Определять канонический репозиторий, parent/upstream и default branch.
- [ ] Искать существующий PR/MR по head/base, чтобы не создавать дубликат.

#### M11.3. Состояния

Единая модель `ContributionState` с полями `state`, `reason`, `evidence` (какие данные получены)
и `confidence`. Приоритет определения:

1. канонический репозиторий принадлежит текущему аккаунту → `OWN`;
2. есть push в чужой канонический репозиторий → `COLLABORATOR`;
3. `origin` — свой форк с `parent`/`upstream` → `FORK`;
4. remote есть, но push-прав нет и своего форка нет → `READ_ONLY`;
5. нет remote, неизвестный хост, нет авторизации, несколько аккаунтов или API недоступен →
   `UNKNOWN` — с причиной, а не с угадыванием.

- [ ] `OWN` — PR из ветки этого же репозитория.
- [ ] `COLLABORATOR` — PR из ветки чужого канонического репозитория, без форка.
- [ ] `FORK` — push в свой `origin`, PR из форка в `upstream`/parent.
- [ ] `READ_ONLY` — для изменений нужен fork; объяснить это до push, а не после 403.
- [ ] `UNKNOWN` — показать, каких данных не хватает, и дать ручной выбор remote/base/head.
- [ ] Тесты матрицы состояний на моках API; отдельно проверить «клонированный, но свой»,
      «свой форк» и «чужой репозиторий с push-правами».

#### M11.4. Пошаговый сценарий

- [~] Preflight: `git remote -v`, `git branch --show-current`,
      `git status --porcelain=v2 --branch`, `git rev-list --left-right --count <base>...HEAD`,
      `git log --oneline <base>..HEAD`, `git ls-remote --heads <remote> <branch>`. Показать ветку,
      незакоммиченные изменения, ahead/behind, список коммитов и существующий PR.
      Уровень 1 в 1.0 уже показывает branch/upstream/ahead-behind/worktree без сети;
      `ls-remote`, коммиты и сравнение — в уровне 2.
- [ ] `OWN`/`COLLABORATOR`: создать или выбрать ветку → `git push -u <remote> <branch>` →
      открыть compare/PR в том же репозитории.
- [ ] `FORK`: `git push -u origin <branch>` → PR с `base: <upstream>:<default>` и
      `head: <me>:<branch>`; при необходимости `git remote add upstream <url>` и
      `git fetch upstream`.
- [ ] `READ_ONLY`: объяснить fork → открыть страницу создания форка (или API после явного
      подтверждения) → `git remote set-url origin <fork-url>`, `git remote add upstream <url>`,
      `git fetch upstream` → push → PR.
- [ ] `UNKNOWN`: показать недостающие данные, дать выбрать remote/base/head вручную и открыть
      compare URL; не выполнять push, fork или создание PR автоматически.
- [ ] Для каждого шага — точная команда, ожидаемый результат и кнопка copy. Выполнение — только
      после явного подтверждения; никаких скрытых push/fork/PR.
- [ ] PR: сначала compare URL в браузере; при наличии API — `POST /repos/{owner}/{repo}/pulls`
      (GitHub) или `POST /projects/:id/merge_requests` (GitLab), с draft, title/body из коммитов
      и повторной проверкой существующего PR.
- [ ] После создания: draft/open/merged/closed, checks, reviews, mergeability; подсказки «что
      дальше» (update branch/rebase, ответить на review), но без auto-merge.

#### M11.5. Объяснения и безопасность

- [ ] Встроенный глоссарий: clone vs fork, origin vs upstream, base vs head, PR/MR, draft,
      review, checks, merge. Объяснение в контексте шага, а не стена текста.
- [ ] Никаких скрытых действий: push, fork и создание PR — только по кнопке, с превью команды
      и последствий.
- [ ] Токены — только в encrypted store; redaction в логах; без телеметрии; уважать rate limit.
- [x] Первый срез M11 — уровень 1 Custom Git Host для 1.0: разбор всех URL remote,
      `insteadOf`, host/owner/repo и локальный preflight без API-обещаний.
      GitHub и GitLab — первые адаптеры уровня 2 в 1.1. Остальные хосты — после 1.0, в 1.2–1.9,
      по одному и по спросу; self-hosted/enterprise — через настраиваемый API base URL.
- [ ] Проверить на тестовых GitHub/GitLab аккаунтах: own, fork, collaborator, read-only,
      отсутствие сети/токена, два аккаунта, существующий PR.

#### M11.6. Хостинги и порядок адаптеров

Это каталог будущих возможностей, а не обязательство выпустить всё. Каждый адаптер
включается отдельно; его отсутствие не блокирует ни обычные git-операции, ни уровень 1.

**Уровень 1 — Custom Git Host.** Любой хост, у которого remote URL и git-транспорт дают
однозначные host/owner/repo: scp-like, `ssh://`, `https://`, локальные пути, порты,
несколько URL у remote и `insteadOf`. Доступны remote-операции и preflight без API;
провайдерские права, PR/MR и checks остаются `UNKNOWN`, без догадок по имени папки или
email автора. Если сравнение/открытие ссылки нельзя построить безопасно — только ручной URL.

**Уровень 2 — адаптеры хостеров.** Дают identity, права, метаданные репозитория, fork/parent,
PR/MR (или аналог), checks и self-hosted API base URL. Модель PR/MR не считается универсальной.

**Основная очередь.** Эти адаптеры добавляются первыми, по мере спроса и возможности проверить
сценарий:

- **PR/MR-модель:** GitHub, GitLab, Bitbucket, Azure DevOps (Azure Repos), Gitea, Forgejo,
  Codeberg, Gitee, OneDev, Gogs, Assembla, Beanstalk, Backlog.
- **Другая модель review:** Gerrit (changes/refs), SourceHut (mailing lists), Launchpad
  (merge proposals), Phabricator/Phorge (Differential), Radicle (patches/P2P).
- **Особый транспорт/хранение:** AWS CodeCommit (IAM), Hugging Face Hub (LFS/xet).

**Вторичная очередь.** Это резерв на случай, если основная очередь когда-нибудь закончится,
и при наличии времени и желания. Она не входит в текущий порядок работ и не является
обязательством. Каждый адаптер по-прежнему включается отдельно и не блокирует git/уровень 1.

- **Собственная архитектура / отдельный API:** RhodeCode, Fossil, Pijul Nest, Apache Allura,
  Tuleap, SCM-Manager, Heptapod. Здесь нет готового общего core: для каждого нужен свой слой
  identity, прав и review. Fossil и Pijul Nest вообще не Git-хосты — сначала проверить, применим
  ли уровень 1 и какой remote/transport у них реально есть. Heptapod — ответвление GitLab для
  Mercurial; не считать его прямым GitLab-адаптером без проверки API и ограничений.
- **Производные/совместимые архитектуры:** GitBucket (GitHub-совместимый), SourceForge
  (Apache Allura), GForge (наследует SourceForge/Allura). Можно попробовать переиспользовать
  соответствующий core, но сначала проверить расхождения в API, правах и модели review.
- **Новые/экспериментальные:** Tangled, Cloudflare Artifacts. Сначала выяснить, есть ли у них
  стабильный git-remote/API и вообще PR-сценарий; не обещать интеграцию до проверки.

Порядок основной очереди: GitHub и GitLab первыми; Gitea/Forgejo/Codeberg могут делить общий
core адаптера; остальные — по спросу, стабильности API и возможности проверить сценарий без
реального аккаунта. Версии 1.1–1.9 — ориентир, а не жёсткий график. Вторичная очередь идёт
только после неё.

## 5. Критерий «ничего не спрятано» (acceptance для v1.0)

Проверяем вручную, что всё это делается **из UI**, без терминала:

- [ ] Удалить коммит из середины истории (drop в rebase) и сохранить потомков.
- [ ] Отрезать хвост истории (`reset --hard` на старый коммит) и восстановить его из reflog.
- [ ] Изменить сообщение/автора любого коммита, а не только последнего.
- [ ] Squash/fixup/reorder произвольных коммитов drag&drop.
- [ ] Force-push (и `--force-with-lease`, и `--force`) с явным пониманием последствий.
- [ ] Удалить файл/секрет из всей истории (`filter-repo`) с предпросмотром.
- [ ] Удалить ветку/тег на remote.
- [ ] Поправить произвольный ключ в `.git/config`, включая неизвестный приложению.
- [ ] Запустить произвольную git-команду и увидеть её вывод.
- [ ] Отменить последнюю операцию приложения одной кнопкой.
- [ ] Работать с worktree, submodule, stash, LFS, хуками, подписями.
- [ ] Видеть точную команду для каждого действия и копировать её.

## 6. Принятые решения

- [x] **Android**: не входит в 1.0. Сначала desktop-релиз, Android — после. Основной кандидат —
      libgit2/JGit in-process; Termux bridge — только опционально для power users.
- [x] **Системный git на Desktop**: используем системный. Если не найден — предлагаем
      автоматическую установку по кнопке (Windows: Git for Windows; macOS: `xcode-select --install`
      / Homebrew; Linux: пакетный менеджер) с системным подтверждением прав + ручной выбор пути.
      Встроенный git не бандлим.
- [x] **Интеграции с хостингами**: после 1.0, отдельный этап M11 (PR-помощник); в релиз 1.0
      не входят.
- [x] **Стратегия хостингов**: два уровня. Уровень 1 — Custom Git Host: любой хост с разбираемым
      git remote, без API-обещаний. Уровень 2 — адаптеры конкретных хостеров (identity, права,
      PR/MR, checks), которые добавляются в 1.1–1.9 по одному (GitHub/GitLab — в 1.1).
      Каталог и порядок — §M11.6; все адаптеры сразу не обещаем.
- [x] **Хранение секретов**: собственный encrypted store, одинаковый по поведению на всех
      платформах; OS-keychain не используем как хранилище секретов.
- [x] **Лицензия**: GPLv2 (GPL-2.0-only), независимо от того, понадобится ли когда-нибудь
      бандл git. Название — MyBeautifulGit-chan.
- [x] **Синхронизация настроек**: не нужна.

### 6.1. Уточнено

- [x] **Ключ для encrypted store**: device key (OS keystore) + опциональная passphrase
      оборачивают один мастер-ключ; формат, миграция и восстановление — §2.5.
- [x] **Мастер установки git**: минимум 2.30 (compatibility floor), полный набор — с 2.40;
      2.56 не требуем (матрица — §2.6). Порядок: PATH → стандартные пути → реальный
      `git --version` → парсинг версии. Старая версия — предупреждение и список недоступных
      фич; EOL-версия — отдельное предупреждение о безопасности. Не найден — экран установки:
      авто-установка, страница загрузки, ручной путь; проверка сети перед авто-установкой.
      - Windows: `winget install --id Git.Git -e` (права администратора), PortableGit без прав,
        официальный установщик.
      - macOS: `xcode-select --install`, Homebrew, установщик. `/usr/bin/git` — shim: без
        Command Line Tools его не запускать, иначе откроется системный диалог установки.
      - Linux: пакетный менеджер дистрибутива (apt/dnf/pacman/zypper/apk) + страница загрузки;
        версии в LTS-дистрибутивах проверяем по минимальной явно.

## 8. Ориентировочные оценки

Это **не публичный график и не обязательство**: оценки сделаны 2026-11-14 при допущении

(подписи, notarization, тестовые аккаунты, доступы к API). Один час здесь — час работы
с кодом, тестами и сборкой, а не человеко-час. 33 часа overage считаем буфером.
