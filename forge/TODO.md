# Форж: TODO и план

Свой Git-хостинг для Git-chan. Отдельный проект и отдельный документ: продуктовый план приложения —
[../TODO.md](../TODO.md), сайт — [../website/TODO.md](../website/TODO.md).

CI, раннеры и песочница сюда сознательно **не входят** — это следующий разговор и отдельный документ.

## 0. Решение

- [x] **Пишем свой форж с нуля**, без форка Gitea/Forgejo/GitLab и без их архитектуры. Причина —
      полный контроль над требованиями к железу, моделью нагрузки и форматом данных.
- [x] **Транспорт Git не пишем.** Умный HTTP и упаковку объектов отдаём проверенной реализации,
      SSH — готовому серверу. Свой код — выше: права, review, API, фоновые задачи.
- [x] **API-first.** Главный клиент — Git-chan; веб-интерфейс вторичен и минимален.
- [x] **Single-node.** Один процесс, один диск, SQLite; горизонтальное масштабирование — не цель.
- [ ] CI — отдельный документ: [../ci/TODO.md](../ci/TODO.md).
- [ ] Git LFS, issues, wiki, packages, поиск — не в MVP (см. раздел 6).

Кого это не касается: уровень 1 в приложении (обычный Git по URL) работает с форжем с первого
дня, как и с любым хостом.

## 1. Что входит в MVP

| Обязательно | Позже | Не делаем |
|---|---|---|
| git clone/fetch/push по HTTPS и SSH | веб-UI с diff и комментариями | CI и раннеры |
| аккаунты, токены, базовые права | email-уведомления | issues, wiki, boards |
| список репозиториев, создание/удаление | организации и команды | packages/registry |
| сравнение веток и diff | веб-редактор файлов | LFS |
| PR: создать, список, комментарии, merge | ревью-аппрувы, draft | forks и upstream-модель |
| вебхуки | audit log, квоты | SSO/SAML, федерация |
| бэкап и восстановление | поиск по коду | мобильный клиент |

## 2. Архитектура

### 2.1 Компоненты

- **Caddy** — TLS, HTTP/2, сжатие, прокси на локальный порт. Конфиг рядом с сайтом.
- **Приложение** — один процесс: API, рендеринг минимальных страниц, git-транспорт.
- **Хранилище объектов** — bare-репозитории на диске, `<data>/repos/<uuid>.git`. Никакой БД внутри
  git-каталога: только файлы, которые git создаёт сам.
- **Метаданные** — SQLite (WAL). Пользователи, токены, репозитории, права, PR, комментарии, события.
  Миграция на PostgreSQL — только если появится второй узел или аналитика.
- **Фоновые задачи** — таблица `jobs` в SQLite + один воркер в том же процессе: пересчёт ссылок,
  `gc --auto`, доставка вебхуков с ретраями.

### 2.2 Транспорт

- **JGit** (Eclipse) — smart HTTP v2, потоковая упаковка, `UploadPack`/`ReceivePack`. Библиотека
  используется в тысячах проектов и получает свои патчи безопасности — это осознанная зависимость,
  а не «свой парсер пакетов».
- **Apache MINA sshd** — SSH-доступ поверх тех же репозиториев.
- Альтернатива без JVM: `git http-backend` как CGI + системный `sshd` с `git-shell`. Чуть дешевле
  по памяти, но добавляет зависимость от системного git и сложнее в упаковке.
- **Чего не делаем:** свой разбор pack-файлов, свой протокол, свои хуки на уровне объектов.

### 2.3 Бюджет нагрузки и памяти

Цель — 1 vCPU / 1–2 ГБ RAM и предсказуемое поведение под нагрузкой:

- JVM-процесс: heap 384–512 МБ, G1, `MaxRAMPercentage` от лимита контейнера; базовый RSS ~200 МБ.
- Пакеты не буферизуем в памяти: стриминг от диска в сокет, лимит на размер push.
- Ограниченная очередь запросов (например, 32 одновременных git-операции) — лишние ждут, а не
  съедают память.
- Таймауты: заголовки 10 с, тело запроса 5 мин, простаивающее соединение 30 с.
- Квоты: на репозиторий (диск), на пользователя (число репозиториев), на размер одного push.
- `gc --auto` в фоне с низким приоритетом, никогда в обработчике запроса.
- Целевые показатели: p95 API < 150 мс, clone небольшого репозитория < 2 с локально,
  push без блокировки других операций.

### 2.4 Модель данных (минимум)

`users`, `tokens` (hash, scopes, last_used), `repos` (id, owner, name, path, default_branch,
visibility, quota), `collaborators` (repo, user, role), `refs_cache` (repo, ref, sha, updated_at),
`pull_requests` (repo, number, title, body, head, base, state, merge_commit),
`pr_comments`, `events` (для вебхуков и ленты), `jobs`, `webhooks`.

### 2.5 API

Версия `/api/v1`, JSON, токен в `Authorization: Bearer`. По возможности **повторяем форму GitHub**
там, где семантика совпадает: это позволяет клиенту переиспользовать GitHub-адаптер, а не писать
третий. Расхождения фиксируем в документе API.

Минимум:

- `GET /user`, `POST /tokens`
- `GET/POST /repos`, `GET/DELETE /repos/{owner}/{name}`
- `GET /repos/{owner}/{name}/branches`, `/commits`, `/compare/{base}...{head}`
- `GET/POST /repos/{owner}/{name}/pulls`, `GET/PATCH /pulls/{number}`
- `POST /pulls/{number}/comments`, `PUT /pulls/{number}/merge`
- `POST /repos/{owner}/{name}/webhooks`

### 2.6 Веб-хуки и события

События: `push`, `repository`, `pull_request`. Доставка — из таблицы `jobs`, ретраи с
экспоненциальной задержкой, подпись HMAC в заголовке. Без гарантии порядка: порядок обеспечивает
получатель по `X-Event-Id`.

## 4. Приёмка MVP

- [ ] `git clone`, `fetch`, `push` по HTTPS и SSH на реальном репозитории, protocol v2 включён.
- [ ] Shallow clone и push в существующую ветку; конкурентный push двух клиентов не портит репозиторий.
- [ ] Неверный токен — `401`, чужие права — `403`, превышение квоты — `413`/`409`, никогда `500`.
- [ ] PR: создать из форка-ветки, прокомментировать, смёржить, увидеть состояние в клиенте.
- [ ] Вебхук доставлен и повторён при ошибке.
- [ ] Бэкап снимается и восстанавливается на чистую машину без потери объектов и метаданных.
- [ ] Под нагрузкой (10 параллельных clone) RSS процесса остаётся в бюджете, p95 API в норме.

## 5. Риски

- **Безопасность ввода.** Git-протокол, SSH, markdown, вебхуки — всё принимает чужие данные.
  Поэтому транспорт не свой, а лимиты и таймауты — обязательная часть MVP, а не «потом».
- **CVE на зависимостях.** JGit и MINA получают патчи; нужно следить и обновляться. Это цена
  зависимости, но она ниже, чем цена собственного парсера пакетов.
- **Single-node.** Один диск — одна точка отказа: бэкап на другой носитель вне сервера обязателен.
- **Рост объектов.** История только растёт: квоты и `gc` нужны до появления первых чужих репозиториев.
- **Abuse.** Публичный push-эндпоинт притягивает мусор: регистрация по приглашению и лимиты с первого дня.
- **JVM и 1 ГБ.** Возможна экономия на `git http-backend`, если heap окажется тесен.

## 6. Не сейчас

CI и раннеры, LFS, issues и вики, packages/registry, поиск по коду, организации и команды,
форки и upstream, SSO, федерация, веб-редактор, мобильный клиент. Всё это — по спросу и без
обещаний.

## 7. Альтернативы (только для справки)

- **Forgejo** — 2–4 часа на развёртывание, ~150 МБ в простое, SQLite хватает на 10 человек,
  API близок к GitHub-форме. Не выбрано: своя архитектура и контроль нагрузки важнее готового UI.
- **Gitea** — то же по весу, MIT, компания-владелец. Не выбрано по той же причине.
- **GitLab CE** — 8 vCPU / 16 ГБ в базовой конфигурации, ~5.5 ГБ в простое, месячные релизы.
  Не выбрано: на порядок дороже по железу.
- **Форк Forgejo/Gitea** — наследует сто тысяч строк, но и поток CVE с обязанностью мержить
  security-патчи. Живёт у фонда Codeberg с командой; для одного разработчика это худший из миров.
- **`git http-backend` вместо JGit** — не альтернатива архитектуре, а вариант транспорта:
  дешевле по памяти, но зависит от системного git. Оставить как запасной путь для Ф0.

## 8. Открытые вопросы

1. Язык сервера: Kotlin/Ktor + JGit (общая база знаний с приложением) или Go/Rust с `gix`.
2. SQLite до какого масштаба терпим, и по какому признаку переезжаем на PostgreSQL.
3. Домен: `git.baconana.com`, `forge.git-chan.baconana.com` или отдельный.
4. Ставить форж на тот же VPS, что сайт, или на отдельный (сайт уже занимает pm2 и порт).
5. Насколько жёстко следовать GitHub-форме API ради переиспользования клиента.
6. Политика регистрации: открытая, по приглашению, только свои аккаунты.
