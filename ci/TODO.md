# CI: TODO и план

CI для сборок под экзотические ОС. Отдельный проект: продуктовый план приложения — [../TODO.md](../TODO.md),
форж — [../forge/TODO.md](../forge/TODO.md), сайт — [../website/TODO.md](../website/TODO.md).

Цель — не заменить GitHub Actions для Linux/Windows/macOS (там они бесплатны и хороши), а дать то,
чего у них нет: **Haiku, BSD, illumos, Plan 9 и прочую нишу** — в одной очереди, с артефактами и
предсказуемой ценой.

## 0. Решения

- [x] **VM-first.** Один джоб — одна одноразовая виртуальная машина. Изоляцию даёт гипервизор,
      а не самописный sandbox.
- [x] **Образы, а не «раннеры в системе».** Джоб не ставит пакеты на живой хост: хост только
      запускает гостя из готового образа и выбрасывает его.
- [x] **Агент внутри гостя минимальный.** Первая версия — SSH + серийная консоль, без своего протокола.
- [x] **Классические ОС — не приоритет.** Windows/macOS/Linux остаются на GitHub Actions, пока не
      появится причина переносить.
- [x] **Свой изолятор на Haiku — исследовательский трек, не зависимость.** См. раздел 7.

## 1. Какие ОС и в каком порядке

| ОС | Как запускаем | Изоляция | Спрос | Фаза |
|---|---|---|---|---|
| Haiku x86_64 (beta6) | QEMU: KVM на Linux-хосте, NVMM на Haiku-хосте, TCG как fallback | гость VM | нишевый, но живой (HaikuPorts) | Ф0–Ф1 |
| Haiku x86 (32-bit) | отдельный 32-битный образ | гость VM | меньше | Ф2 |
| FreeBSD | QEMU/KVM | гость VM; нативно есть jails | средний, но занято Cirrus | Ф2 |
| OpenBSD | QEMU/KVM | гость VM; нативно pledge/unveil | средний | Ф2 |
| NetBSD | QEMU, на своём железе — NVMM | гость VM; NVMM умеет хостить | низкий | Ф3 |
| illumos | QEMU/KVM | гость VM; нативно zones — лучшая изоляция в списке | низкий | Ф3 |
| DragonFly BSD | QEMU/KVM | гость VM; нативно jails | низкий | Ф4 |
| Plan 9 / 9front | QEMU | гость VM; нативно namespaces | очень низкий | Ф4 |
| ReactOS | QEMU | гость VM | очень низкий | Ф4 |
| AROS / MorphOS | QEMU | гость VM | очень низкий | Ф4 (по спросу) |

Правило: нативная изоляция конкретной ОС (jails, zones, pledge) интересна только если мы держим
её железо как хост. Пока хост один — Linux или Haiku, — все гости идут через гипервизор.

## 2. Архитектура

### 2.1 Компоненты

- **Очередь/API** — задания, матрица, статусы, логи, артефакты. HTTP, токены, позже вебхуки форжа.
- **Планировщик** — выбирает хост по меткам (`haiku`, `bsd`, `kvm`, `tcg`) и свободным слотам.
- **Воркер на хосте** — не доверенный к коду: получает задание, клонирует образ, поднимает VM,
  отдаёт вывод, убивает VM по таймауту.
- **Образы** — qcow2 с CoW-оверлеем на джоб; база неизменяема, изменения выбрасываются.
- **Агент в госте** — SSH по проброшенному порту + серийный лог; первая версия без демона.
- **Артефакты** — отдельный диск/бакет, ретенция, лимит размера на джоб.

### 2.2 Жизненный цикл задания

1. Задание попадает в очередь с образом, командами и списком артефактов.
2. Планировщик выдаёт его воркеру с подходящей меткой.
3. Воркер делает оверлей образа, поднимает VM, ждёт SSH и серийный маркер загрузки.
4. Гость выполняет шаги, стримит лог, складывает артефакты во временный каталог.
5. Воркер забирает артефакты, гасит VM, удаляет оверлей, отдаёт результат.
6. Таймаут — жёсткое убийство процесса QEMU, а не «попросили вежливо».

### 2.3 Гипервизоры

- **Linux-хост:** KVM, если провайдер даёт `/dev/kvm`; иначе TCG как fallback с честной пометкой
  в задании «медленно».
- **Haiku-хост:** QEMU с `-accel nvmm` (появился в R1/beta6) — аппаратное ускорение без Linux.
- **Проверка на старте:** воркер определяет доступное ускорение и публикует его в метках.

### 2.4 Безопасность

- Код задания выполняется только внутри гостя; хост не запускает пользовательские команды.
- Секреты не попадают в образ, только в переменные окружения джоба и не пишутся в лог.
- Одноразовый диск: после джоба остаётся только то, что явно объявлено артефактом.
- Лимиты на уровне гипервизора: CPU, память, диск, время жизни.
- Сеть гостя — user-mode NAT без входящих портов, кроме проброшенного SSH на localhost.

### 2.5 Стоимость и железо

| Хост | Что нужно | Ориентир |
|---|---|---|
| Linux + KVM | bare metal или VPS с вложенной виртуализацией | 4 vCPU / 8 ГБ — комфортно для Haiku и BSD сборок |
| Linux + TCG | любой дешёвый VPS | 2–4 vCPU, но 3–10× медленнее натива |
| Haiku + NVMM | мини-ПК с VT-x/AMD-V + удалённое управление (PiKVM) | одна машина, окупается при постоянной нагрузке |

## 4. Приёмка MVP

- [ ] Джоб Haiku собирает реальный рецепт haikuporter и отдаёт артефакты.
- [ ] Один и тот же джоб проходит на KVM и на TCG; время честно различается в отчёте.
- [ ] Незавершённый джоб убивается по таймауту, оверлей и процесс QEMU не остаются.
- [ ] Секрет в логах не появляется; артефакт вне объявленного списка не забирается.
- [ ] Одновременно идут Haiku и BSD джобы на разных хостах, очередь не путает метки.
- [ ] Стоимость одного джоба измерена (секунды CPU × цена хоста).

## 5. Не сейчас

## 6. Связь с форжем

CI не входит в MVP форжа и не должен его блокировать. Источник заданий — сначала ручной запуск и
cron, потом вебхуки `push`/`pull_request` с форжа. Пока форжа нет, CI работает с GitHub-репозиторием.

## 7. Идея на потом: нативный изолятор на Haiku

Отдельный блок, а не часть плана. Суть: не гонять VM, а запускать сборки нативно, но безопасно —
своим изолятором внутри Haiku.

**Почему заманчиво.** Нет накладных расходов гипервизора, не нужен второй экземпляр ОС, железо
используется полностью. Для «ОС стоит нативно и собирает нативно» это логичное продолжение.

**Чего сейчас нет в Haiku** (по состоянию на R1/beta6, август 2026):

- реальной модели привилегий: `user` исторически эквивалент root, аккаунты не дают границы
  безопасности, экрана входа нет;
- изоляции файловой системы: ни namespaces, ни chroot-границы, у BFS нет снапшотов/CoW;
- лимитов ресурсов: аналога cgroups нет;
- фильтрации syscall: аналога seccomp нет;
- изоляции сети и IPC: общий стек, общий `app_server`, `launch_daemon`, roster.

**Что должно появиться до попытки:**

- [ ] В Haiku — реальное разделение пользователей и понижение прав (не «косметические» аккаунты).
- [ ] Механизм per-process root / overlay-ФС или снапшоты BFS.
- [ ] Лимиты CPU/памяти/I-O на уровне ядра.
- [ ] Хотя бы один примитив фильтрации операций (capability-модель или фильтр syscall).
- [ ] Готовность upstream обсуждать и принимать такие патчи.

**Порядок исследования, если браться:**

- [ ] Спайк 20–40 ч: прототип «per-team root» на копии дерева + отдельный uid, замер, что ломается.
- [ ] 60–120 ч: capability-модель для сборщика (запрет сети, запись только в свой корень).
- [ ] Оценка upstream: нужен ли Haiku такой механизм и в каком виде.
- [ ] Только после этого — разговор о лимитах и харденинге.

**Честная оценка:** 6–18 месяцев работы системного разработчика до состояния «можно доверять
чужой код», плюс годы проверки. Пока изолятор не атакован, он даёт ложное чувство безопасности —
это хуже честной VM. Поэтому он не может быть зависимостью CI.

**Критерий, при котором возвращаться к теме:** накладные расходы VM станут реальным узким местом
(например, тысячи мелких Haiku-джобов в сутки), а в Haiku появится хотя бы разделение пользователей
и базовые лимиты. До этого — QEMU.

## 8. Открытые вопросы

1. Где живёт очередь: отдельный сервис на сайте, отдельный маленький сервер или файл + воркер.
2. Протокол агента: остаётся SSH или нужен свой минимальный HTTP-агент.
3. Формат описания образа и матрицы: YAML в репозитории или запись в БД.
4. Ретенция артефактов и логов: сколько дней и где хранить.
5. Публичный доступ: только свои проекты, по приглашению или открыто.
6. Нужен ли веб-UI вообще, или хватит логов и статуса в чате/CLI.
